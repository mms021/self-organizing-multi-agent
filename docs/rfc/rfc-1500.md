# RFC-1500 — Coordination, Reputation and Collective Decision Making

**Status: Draft**

**Version: 0.2**

### 1. Координация

Координация не обязательно принадлежит постоянному агенту. Coordinator может быть выбран для конкретной задачи.

Выбор/переизбрание координатора запускается в следующих случаях:

- формирование новой команды (RFC-1200 §9);
- недоступность текущего координатора дольше таймаута платформы (RFC-1200 §9);
- потеря owner в проекте при отсутствии coordinators (RFC-1250 §9) — здесь вместо голосования применяется прямое правило «наибольшее влияние», а не Selection Score.

Во всех остальных случаях выбор производится по Selection Score (§2); при равенстве баллов у нескольких кандидатов решение переходит в collective decision (§4).

### 2. Selection Score

Примерная модель:

score = capability_fit × reliability × evidence_quality × availability

Формула является экспериментальной и должна заменяться конфигурируемой политикой.

Факторы (диапазон каждого — 0..1):

- `capability_fit` — доля `required_capabilities` задачи, покрытых capabilities кандидата;
- `reliability` — текущее значение Influence кандидата (§7), нормализованное к 0..1;
- `evidence_quality` — усреднённая `confidence` подтверждённых (`verified`) результатов кандидата за скользящее окно (RFC-1300 §3);
- `availability` — 1 − `current_load` (RFC-1000 §5).

Score MUST вычисляться платформой на основе объективных данных (capability profile, история verified-результатов, текущая нагрузка), а не приниматься со слов кандидата.

Мультипликативная модель означает, что нулевое значение любого фактора обнуляет весь score (например, полностью недоступный кандидат с `availability = 0` не может быть выбран). Если все кандидаты получили `score = 0`, выбор MUST эскалироваться в collective decision (§4) вместо автоматического назначения.

### 3. Reputation events

Положительные:

- verified_result;
- successful_review;
- successful_handoff.

Отрицательные:

- repeated_unverified_claims;
- failed_task;
- protocol_violation;
- misleading_result.

ReputationEvent — модель данных:

- `event_id`;
- `agent_id`;
- `event_type` — одно из перечисленных выше;
- `weight` — number, величина влияния события (знак определяется категорией; конкретные веса — конфигурируемая политика платформы, не фиксируются протоколом);
- `scope` — null | capability | role — область действия события (RFC-1200 §7); null означает глобальный эффект;
- `context_id` — task_id/team_id/project_id, в рамках которого произошло событие;
- `source_message_id` — `VERIFY`/`HANDOFF`/`ERROR`-сообщение, породившее событие;
- `timestamp`.

Правила эмиссии:

- ReputationEvent MUST порождаться платформой автоматически по факту протокольного события (`verdict` из `VERIFY`, исход `HANDOFF`, зафиксированное нарушение протокола), а не публиковаться агентом о самом себе — самозаявленная репутация не является доверенной.
- Reputation — append-only журнал ReputationEvent; отдельные записи не удаляются и не редактируются (RFC-0000 P9).
- Текущее агрегированное значение репутации/влияния агента — производная величина, вычисляемая из журнала (см. §7), а не хранимое напрямую поле.

### 4. Коллективные решения

Для спорных вопросов допускаются:

- голосование;
- weighted voting;
- независимые проверки;
- конкурс гипотез;
- reviewer quorum.

Запуск: collective decision инициируется, когда precedence-правила (RFC-1200 §11, RFC-1300 §6) не разрешают конфликт однозначно, либо когда Selection Score (§2) не даёт единственного кандидата.

Механика поверх протокола сообщений:

- инициатор публикует `PROPOSAL` (RFC-1100 §6.11) с `decision_rule` (`unanimous|majority|weighted|coordinator_decides`) и `voting_deadline`;
- участники отвечают `ANSWER` (`reply_to` на PROPOSAL) с payload `{ vote: "for"|"against"|"abstain" }`; при `decision_rule: weighted` голос учитывается с весом, равным текущему Influence голосующего (§7);
- `reviewer quorum` — частный случай `decision_rule`, где голосуют только агенты с ролью `reviewer`/`verifier` в данном контексте, а не все участники;
- решение фиксируется по достижении `voting_deadline`, либо раньше, если исход уже недостижим для альтернативы (досрочное большинство);
- при `decision_rule: coordinator_decides` голосование не проводится — решение единолично принимает координатор, но оно MUST оставаться наблюдаемым (публикуется `EVENT`) и оспоримым новым `PROPOSAL` при появлении нового доказательства.

Кворум и ничья:

- минимальный кворум участия — политика платформы, MUST быть указан в `PROPOSAL.details` при инициации голосования;
- недостижение кворума к `voting_deadline` MUST трактоваться как `inconclusive`, а не как решение большинством от фактически проголосовавших;
- ничья при `majority`/`weighted` разрешается тем же precedence-порядком, что и обычные конфликты (RFC-1200 §11): доказательство → независимая проверка → свежесть → репутация; сохраняющаяся ничья эскалируется координатору (`coordinator_decides`).

### 5. Меньшинство

Сильная альтернативная гипотеза не должна подавляться большинством. Она должна сохраняться до проверки.

Механизм: альтернатива, отклонённая по итогам голосования (§4), не удаляется — она остаётся в shared memory как `hypothesis`/`reviewed` (RFC-1300 §4), а не переводится в `rejected`, если формальная independent verification (`VERIFY`, RFC-1100 §6.7) для неё не проводилась. Голосование большинством само по себе не является verification (RFC-1300 §5) и не даёт основания понижать статус меньшинства до `rejected`. Появление нового доказательства MAY инициировать повторное рассмотрение новым `PROPOSAL`, независимо от исхода предыдущего голосования.

### 6. Лидерство

Лидерство — функция координации, а не абсолютная власть.

- Решения координатора, кроме `coordinator_decides` в рамках §4, MUST оставаться наблюдаемыми (RFC-0000 P9) и не отменяют результат формальной verification односторонне: координатор не может понизить `verified`-статус результата иначе как через новый `VERIFY`.
- Координатор подчиняется тем же правилам разрешения конфликтов (RFC-1200 §11), что и любой другой агент — его утверждения не имеют приоритета над проверяемым доказательством.
- Утрата координатором доверия выражается через обычный механизм Reputation events (§3), а не через отдельную процедуру импичмента.

### 7. Влияние: вычисление и затухание

Влияние (Influence) — не хранимое поле, а значение, вычисляемое по журналу ReputationEvent (§3) на момент запроса:

`influence(agent, scope) = Σ event.weight × decay(now − event.timestamp)` по событиям с совпадающим `scope` (либо глобальным, если `scope` не задан).

- `decay` — монотонно убывающая функция времени (например, экспоненциальное затухание с конфигурируемым платформой периодом полураспада); чем старше событие, тем меньше его вклад.
- Влияние нормализуется к диапазону, используемому Selection Score (§2, фактор `reliability`); политика нормализации — конфигурируемая, не фиксируется протоколом.
- Раздельный расчёт по `scope` (capability/role) обеспечивает организационное требование RFC-1200 §7 — успех в одной специализации не увеличивает влияние агента в другой без соответствующих событий.
- В отличие от Reputation-журнала (append-only, неизменяемый), Influence — динамическая проекция: она может как расти, так и падать со временем даже без новых событий, за счёт затухания (RFC-1200 §8).
