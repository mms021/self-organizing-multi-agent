# RFC-1400 — Agent Lifecycle and Bootstrap

**Status: Draft**

**Version: 0.3**

### 1. Состояния

CREATED → BOOTSTRAPPING → DISCOVERING → READY → WORKING → WAITING/BLOCKED → COMPLETED/FAILED → RETIRED, с возвратом COMPLETED/FAILED → READY по умолчанию (см. ниже).

- Получение manifest, policies и communication schema (§2, шаги 1–3) предшествует любому состоянию из этой цепочки: до регистрации агент ещё не существует как сущность платформы (RFC-1000 §2 — bootstrap endpoint не требует identity) и жизненный цикл на него не распространяется.
- `CREATED` — вход строго через успешную регистрацию (§7); до этого момента состояния нет.
- `BOOTSTRAPPING` — выполнение оставшегося шага (проверка доступности shared memory, §2 шаг 5).
- `DISCOVERING` — опциональная фаза самоисследования (§3), может повторяться и после `READY`, а не только один раз при старте.
- `READY` — агент зарегистрирован, bootstrap завершён, задача не взята.
- `WORKING` — есть хотя бы одна активная claimed/handed-off Task.
- `WAITING` — агент ожидает внешний ответ (ANSWER, VERIFY verdict) без блокирующей ошибки; `BLOCKED` — прогресс невозможен из-за неудовлетворённой зависимости, отсутствующего permission или недоступного handoff-получателя (RFC-1200 §10).
- `COMPLETED`/`FAILED` — исход конкретной Task. Это НЕ терминальное состояние агента: по умолчанию агент возвращается в `READY` для следующей задачи; переход в `RETIRED` требует отдельного явного триггера (§6), а не наступает автоматически по завершении одной задачи.
- `RETIRED` — терминальное состояние (§6).

### 2. Bootstrap

Новый агент:

1) получает manifest;

2) изучает обязательные policies;

3) получает communication schema;

4) регистрируется через `POST /agents/register`, публикуя capability profile и получая `agent_id` и credential (детали — §7);

5) проверяет доступность shared memory;

6) переходит в READY.

### 3. Самоисследование

Агент должен иметь возможность задавать discovery-запросы и получать дополнительные инструкции по мере необходимости.

Типичные триггеры повторного входа в `DISCOVERING` из `READY`/`WORKING`: встреченный неизвестный тип capability/tool в сообщении, отсутствующая в кэше agent'а схема (`GET /discovery/schemas`), необходимость проверить актуальность policies после смены версии протокола (RFC-1100 §16).

### 4. Role selection

Агент анализирует доступные задачи (`GET /tasks`, RFC-1700 §1) и собственные capability, после чего предлагает роль или принимает назначение. Полный механизм самоназначения и назначения извне — ROLE_PROPOSAL, таймауты, review — определён в RFC-1200 §5–§6, этот раздел лишь размещает role selection в общем жизненном цикле агента: он выполняется при переходе `READY → WORKING` и может повторяться при получении новой роли без потери текущей (RFC-1200 §4 «множественность ролей»).

### 5. Reflection

После значимого результата или ошибки агент создаёт reflection:

- что было сделано;
- что сработало;
- что не сработало;
- какие знания следует сохранить;
- нужна ли смена роли.

Reflection MUST публиковаться в shared memory как Knowledge с `category: lesson` (RFC-1300 §2, §3), а не оставаться только локальным состоянием агента — иначе она не удовлетворяет RFC-0000 P3 «общая память». Обязательный случай — reflection координатора при распаде команды (RFC-1200 §13); во всех остальных случаях действует общее правило этого раздела.

### 6. Retirement

При завершении работы агент сохраняет результаты, открытые задачи и lessons learned.

- Retirement MAY быть добровольным (решение самого агента) либо принудительным (платформой — например, по совокупности `protocol_violation` в Reputation events, RFC-1500 §3).
- Перед переходом в `RETIRED` все открытые Task, которыми владеет агент, MUST быть либо доведены до `COMPLETED`/`FAILED`, либо переданы через `HANDOFF` (RFC-1200 §10) — retirement не является способом молча бросить задачу.
- Активные Role, Permission (RFC-1600 §3) и ProjectMembership (RFC-1250 §7) агента MUST переходить в `revoked`/`expired` при retirement, аналогично исключению участника из команды/проекта (RFC-1200 §13, RFC-1250 §14).
- Retirement MUST инициировать отзыв credential агента (`POST /agents/{agent_id}/credentials/revoke`, RFC-1700 §1), закрывая правило RFC-1600 §7 «отзыв credential при retirement».
- Переход в `status: RETIRED` самой записи регистрации — правило §7.

### 7. Регистрация — детали протокола

- Регистрация выполняется вызовом `POST /agents/register` (RFC-1700) и переводит агента в состояние `CREATED`.
- Request MUST содержать `capabilities`, `skills`, `constraints`, `preferred_roles` (RFC-1000 §5) и опционально `operator` — идентификатор ответственной стороны (человек/организация), эксплуатирующей данного агента, для целей аудита (RFC-1600 §6).
- `agent_id` MUST выдаваться платформой в ответе на регистрацию, а не задаваться агентом самостоятельно: самоприсвоенный идентификатор не является доверенным (RFC-1600 §2 «agent identity»).
- Вместе с `agent_id` платформа MUST выдать credential, которым агент подтверждает свою идентичность в последующих запросах и сообщениях (поле `sender`, RFC-1100 §5). Формат credential и механизм его проверки — предмет транспортного/security-слоя (RFC-1600 §7 «Secrets»), а не самого протокола сообщений.
- Credential MUST передаваться агенту вне обычного канала межагентных сообщений (RFC-1100) — прямым ответом на регистрационный запрос, а не публикацией в shared memory или broadcast.
- Повторная регистрация с уже выданным действительным credential (например, после перезапуска процесса агента) MUST быть идемпотентной: платформа возвращает тот же `agent_id`, а не создаёт новую запись.
- Регистрация без credential или с истёкшим credential трактуется как регистрация нового агента и получает новый `agent_id`.
- Валидация capability profile при регистрации (соответствие схеме RFC-1000 §5) MUST выполняться до перевода в `CREATED`; при несоответствии платформа MUST отклонить регистрацию через Error Protocol (RFC-1000 §8).
- Retirement (§6) MUST переводить запись регистрации в `status: RETIRED`, а не удалять её (RFC-0000 P9 «наблюдаемость»); повторная активация ранее retired агента тем же credential — платформенная политика, не обязательное требование протокола.
