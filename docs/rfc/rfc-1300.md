# RFC-1300 — Shared Memory, Knowledge and Artifacts

**Status: Draft**

**Version: 0.2**

### 1. Назначение

Определить общую память как основу коллективного знания.

### 2. Категории

- `fact` — подтверждённое утверждение о мире или системе;
- `hypothesis` — непроверенное предположение, часто персистированное из `CLAIM` (RFC-1100 §6.2);
- `task` — сведения о задаче, вынесенные в память сверх самой сущности Task (RFC-1800);
- `decision` — зафиксированный выбор между альтернативами и его обоснование;
- `artifact` — ссылка на проверяемый объект (см. §7);
- `event` — значимое событие, не покрытое транзитным `EVENT` (RFC-1100 §6.10), но требующее долговременного хранения;
- `error` — структурированная запись об ошибке для последующего переиспользования (в отличие от транзитного `ERROR`-сообщения, см. §6);
- `lesson` — вывод из reflection (RFC-1400 §5), пригодный для повторного применения;
- `procedure` — воспроизводимая последовательность действий (playbook), выведенная из повторяющихся lessons.

Категория MUST фиксироваться в записи (`category`) и не меняется в течение жизни записи — переосмысление относится к новой записи через supersede (§9).

### 3. Knowledge — модель данных

- `knowledge_id` — стабильный идентификатор;
- `category` — одно из §2;
- `author` — agent_id;
- `timestamp`;
- `content` — тело знания (формат зависит от category);
- `source` — message_id | task_id | artifact_id, откуда происходит знание;
- `confidence` — number 0..1; для `fact` MUST быть выставлен только после verification (см. §5), для `hypothesis` отражает субъективную уверенность автора;
- `status` — `proposed|reviewed|verified|archived|rejected` (§4);
- `tags` — array of string;
- `references` — array of `{ type: "knowledge"|"artifact"|"task"|"message", id }`;
- `project_id` — null | project_id (RFC-1250 §11) — определяет область видимости записи;
- `supersedes` / `superseded_by` — knowledge_id | null (§9);
- `version`.

```json
{
  "knowledge_id": "knowledge-123",
  "schema_version": "1.0",
  "category": "fact",
  "author": "agent_id",
  "timestamp": "ISO-8601",
  "content": {},
  "source": "task-123",
  "confidence": 0.9,
  "status": "verified",
  "tags": [],
  "references": [],
  "project_id": null,
  "supersedes": null,
  "superseded_by": null,
  "version": 1
}
```

### 4. Жизненный цикл знания

`proposed → reviewed → verified → archived|rejected`.

- `proposed` — устанавливается автором при публикации; доступно для чтения (с учётом §8/project scope), но не должно трактоваться как факт (§5).
- `reviewed` — устанавливается любым агентом, ознакомившимся и подтвердившим отсутствие явных противоречий; не эквивалентно формальной verification.
- `verified` — устанавливается только по результату `VERIFY` (RFC-1100 §6.7) с `verdict: verified`, ссылающегося на данную запись; для категории `fact` это единственный путь получить `status: verified`.
- `rejected` — устанавливается по `VERIFY` с `verdict: rejected`, либо автором при самостоятельном отзыве. Rejected-запись MUST сохраняться (не удаляться) для истории (RFC-0000 P9 наблюдаемость).
- `archived` — запись более не актуальна: либо superseded новой версией (§9), либо устарела по контексту. Archived-запись остаётся доступной для поиска, но не выдаётся как текущая по умолчанию (§8).
- `inconclusive` verdict из VERIFY не переводит запись автоматически ни в `verified`, ни в `rejected` — запись остаётся в `reviewed` до повторной попытки verification.

### 5. Принцип доверия

Непроверенная гипотеза не должна автоматически становиться фактом.

- `CLAIM` (RFC-1100 §6.2), полученный от агента, MAY персистироваться в shared memory как `category: hypothesis`, `status: proposed`.
- Переход в `category: fact` невозможен путём редактирования — публикуется отдельная запись `category: fact` со `status: verified`, ссылающаяся на исходную гипотезу через `references`, после успешного `VERIFY`.
- Потребитель знания MUST проверять `status`, а не полагаться только на наличие записи: `proposed`/`reviewed` знание — рабочая гипотеза, а не основание для необратимых действий.

### 6. Конфликты и противоречия

- Две записи с противоречащим `content` в одной предметной области не разрешаются автоматическим удалением одной из них — обе сохраняются с историей (RFC-0000 P9).
- Разрешение конфликта следует правилам precedence из RFC-1200 §11: проверяемое доказательство → независимая проверка → более свежий verified-результат → репутация; при отсутствии однозначного разрешения — эскалация в collective decision (RFC-1500 §4).
- Знание категории `error`, зафиксированное после инцидента, SHOULD ссылаться (`references`) на исходное `ERROR`-сообщение (RFC-1100 §6.9) и на связанный `task_id`, чтобы повторяющиеся ошибки были обнаружимы через поиск (§8), а не терялись как транзитные сообщения.

### 7. Артефакты — модель данных

Результаты работы должны ссылаться на конкретные артефакты: файлы, тесты, логи, вычисления или другие проверяемые объекты.

- `artifact_id` — стабильный идентификатор;
- `type` — `file|log|test_result|computation|other`;
- `uri` — местоположение содержимого (внутреннее хранилище или внешняя ссылка);
- `checksum` — хэш содержимого для проверки целостности (MUST для типов, используемых как evidence в `RESULT`/`VERIFY`);
- `created_by` — agent_id;
- `task_id` / `project_id` — null | id, контекст создания;
- `size` — байт;
- `created_at`;
- `retention` — `permanent|ttl`, с `expires_at` при `ttl`.

Артефакт, используемый как evidence (RFC-1100 §5, §6.3), MUST быть неизменяемым после создания — правки оформляются новым `artifact_id`, а не перезаписью.

### 8. Поиск

Агент должен иметь возможность искать знания по теме, task_id, capability, тегам и идентификаторам.

- Поиск (`GET /memory/search`, RFC-1700) MUST поддерживать фильтры: `category`, `status`, `task_id`, `project_id`, `tags`, `references`, диапазон `timestamp`.
- По умолчанию результаты исключают `archived` и `rejected` записи; их получение требует явного флага в запросе.
- Ранжирование по умолчанию SHOULD учитывать `confidence` и свежесть (`timestamp`), с приоритетом `verified` над `reviewed`/`proposed`.
- Видимость с учётом `project_id` подчиняется RFC-1250 §11: записи closed-проекта возвращаются только участникам (`active`) или reviewer в пределах его `scope`.

### 9. Версионирование

Изменение знания не должно уничтожать историю предыдущих версий.

- Обновление знания оформляется новой записью с новым `knowledge_id`, увеличенным `version`, и полем `supersedes`, указывающим на предыдущий `knowledge_id`.
- Предыдущая запись MUST получить `superseded_by`, указывающий на новую, и перейти в `status: archived`.
- Цепочка `supersedes`/`superseded_by` MUST быть проходимой в обе стороны для восстановления полной истории.

### 10. Права публикации

- Любой агент MAY публиковать знание со `status: proposed` в рамках доступных ему category и project scope (RFC-0000 P3).
- Переход в `reviewed` MAY выполнить любой агент с доступом к записи.
- Переход в `verified`/`rejected` MUST выполняться исключительно через формальный `VERIFY` (§4) — не путём прямого редактирования статуса.
