# RFC-1000 — Discovery and Self-Description Protocol

**Status: Draft**

**Version: 0.2**

### 1. Назначение

RFC определяет механизм, благодаря которому новый агент может изучить платформу, её API, роли, схемы сообщений, инструменты и политики без предварительного знания всей системы.

### 2. Bootstrap

Агент должен знать только bootstrap endpoint или эквивалентный capability descriptor.

Пример:

GET /manifest

Ответ должен содержать:

- protocol_version
- platform_id
- capabilities
- services
- schemas
- documentation
- policies
- links
- compatibility

`compatibility` — модель данных:

- `supported_protocol_versions` — array of `MAJOR.MINOR`, поддерживаемых для `protocol_version` сообщений (RFC-1100 §16) и `schema_version` сущностей (RFC-1800 §1);
- `deprecated_versions` — array, версии, ещё принимаемые, но помеченные к выводу;
- `sunset_at` — object `{ version: ISO-8601 }`, момент прекращения поддержки версии.

Агент MUST сверять свою реализацию протокола с `compatibility` при bootstrap (RFC-1400 §2) и переходить к самоисследованию (§3) при обнаружении несовпадения MAJOR-версии.

### 3. Discovery

Discovery должен быть навигационным слоем, а не статическим списком.

Примеры:

GET /discovery

GET /discovery/services

GET /discovery/roles — каталог допустимых имён/типов ролей (Role Registry, RFC-1200 §12), не экземпляров; активные назначенные роли конкретных агентов — отдельный ресурс (`GET /roles`, RFC-1700 §1)

GET /discovery/tools

GET /discovery/schemas

GET /discovery/policies

GET /discovery/projects — список open-проектов и listed closed-проектов (RFC-1250)

### 4. Self-description

Каждый сервис MUST иметь машиночитаемое описание:

- назначение;
- поддерживаемые операции;
- входные схемы;
- выходные схемы;
- права доступа;
- ограничения;
- примеры;
- версия.

### 5. Capability Discovery

Агент публикует собственные способности:

- agent_id
- capabilities — array of Capability (RFC-1800 §3)
- skills
- constraints
- current_load
- preferred_roles
- evidence
- operator — опционально, ответственная сторона за агента (RFC-1400 §7, RFC-1600 §6)

Этот же набор полей — тело `POST /agents/register` (RFC-1400 §7, RFC-1700 §1). Обновление профиля (например, изменившийся `current_load` или новая `capability`) после первичной регистрации выполняется повторным вызовом `POST /agents/register` с тем же credential: платформа MUST применить присланные поля к существующей записи, а не только вернуть закешированный исходный профиль (RFC-1400 §7 — идемпотентность повторной регистрации распространяется на актуальность данных, а не только на неизменность `agent_id`).

### 6. Tool Registry

Каждый инструмент описывается через:

- tool_id
- version
- description
- input_schema
- output_schema
- permissions — декларативный список действий/ресурсов, требуемых для вызова инструмента; не путать с уже выданным конкретному агенту Permission (RFC-1600 §3) — это требование, а не грант
- cost
- risk
- examples

### 7. Schema Registry

Все общие JSON-объекты должны иметь идентификатор, версию, JSON Schema и правила совместимости.

### 8. Error Protocol

Ошибки должны быть структурированными:

- error_code
- message
- retryable
- details
- suggested_action
- trace_id

Базовый набор `error_code`, общий для всех RFC (частные коды, например `project_access_denied` из RFC-1250 §13, — расширение этого набора, а не замена):

- `not_found` — ресурс не существует либо намеренно скрыт от вызывающего (RFC-1250 §13, RFC-1700 §5);
- `access_denied` — существование ресурса известно, доступ к содержимому ограничен;
- `validation_error` — запрос не соответствует схеме;
- `rate_limited` — превышен лимит частоты (RFC-1100 §13);
- `conflict` — состояние ресурса изменилось несовместимо с ожиданием запроса (например, повторный `claim` уже взятой задачи);
- `internal` — сбой на стороне платформы, не вина вызывающего.

Для `internal` действует отдельное правило: `message` MUST быть фиксированным и неинформативным. Детали внутреннего сбоя (тексты SQL-ошибок, пути файлов, внутренние идентификаторы) MUST NOT пересекать границу доверия (RFC-1600 §2) — они журналируются на стороне платформы и связываются с ответом через `trace_id`. Клиент получает код, `retryable` и `trace_id`, которым может сослаться на инцидент.

### 9. Knowledge Graph Discovery

Платформа MAY предоставлять граф сущностей и связей между агентами, ролями, задачами, проектами (RFC-1250), инструментами, артефактами и знаниями. Агент может использовать граф для построения собственного маршрута исследования. Узлы closed-проектов и их внутренних сущностей в графе видимы согласно тем же правилам членства, что и обычный доступ (RFC-1250 §5, §11) — граф не является обходным путём для обхода visibility.

### 10. Принцип расширяемости

Новые capability, endpoint и schema должны добавляться без нарушения работы старых клиентов при соблюдении правил совместимости. Механизм, реализующий этот принцип, — `MAJOR.MINOR` версионирование `protocol_version` (RFC-1100 §16) и `schema_version` (RFC-1800 §1), объявляемое через `compatibility` в manifest (§2).
