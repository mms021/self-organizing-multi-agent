# RFC-1100 — Agent Communication Protocol

**Status: Draft**

**Version: 0.2**

### 1. Цель

Стандартизировать межагентную коммуникацию и уменьшить свободный шум в диалогах.

### 2. Транспорт и модель доставки

Протокол не привязан к конкретному транспорту (HTTP polling, WebSocket, message bus/broker — Kafka, NATS, Redis Streams и т.п.). Транспорт выбирается реализацией платформы, но MUST соблюдать следующие гарантии:

- Доставка — **at-least-once**. Получатель MUST быть готов получить одно и то же сообщение более одного раза (см. §8 «Идемпотентность»).
- Упорядоченность гарантируется только в пределах одной пары (sender, recipient) для direct-канала. Порядок сообщений в broadcast/team каналах между разными отправителями не гарантируется.
- Direct-сообщения MUST быть буферизованы платформой, если получатель временно недоступен (см. §12).
- Broadcast-сообщения MAY не буферизоваться для offline-агентов — присоединившийся позже агент восстанавливает пропущенный контекст через `GET /messages` или shared memory, а не через историю канала.

### 3. Каналы

- broadcast — сообщения для группы; MAY фильтроваться подписчиком по capability, роли или тегам темы;
- direct — сообщение конкретному агенту;
- team — временный командный канал; создаётся и закрывается вместе с жизненным циклом команды (RFC-1200 §9, §13) — после распада команды канал MUST быть закрыт, отправка в закрытый team-канал MUST возвращать ошибку;
- system — системные события; write-доступ MUST быть ограничен платформой, обычные агенты не публикуют в этот канал напрямую.

### 4. Типы сообщений

TASK, CLAIM, RESULT, QUESTION, ANSWER, PLAN, REQUEST, VERIFY, STATUS, ERROR, EVENT, PROPOSAL, HANDOFF, REVIEW.

### 5. Базовый JSON-контракт (envelope)

```json
{
  "message_id": "uuid",
  "protocol_version": "1.0",
  "type": "RESULT",
  "sender": "agent_id",
  "recipient": "agent_id|broadcast|team_id",
  "timestamp": "ISO-8601",
  "conversation_id": "uuid",
  "task_id": "uuid",
  "priority": "low|normal|high|critical",
  "payload": {},
  "evidence": [],
  "reply_to": null,
  "ttl": null
}
```

Поля envelope не зависят от типа сообщения; специфичные данные MUST помещаться в `payload` по схеме своего типа (§6).

### 6. Payload-схемы по типам сообщений

#### 6.1 TASK

Описывает цель, контекст, ограничения, критерии готовности и требуемый результат.

- `objective` — string, обязательное;
- `context` — object;
- `constraints` — array of string;
- `required_capabilities` — array of string;
- `success_criteria` — array of string;
- `deadline` — ISO-8601 | null.

Соответствует сущности `Task` из RFC-1800.

#### 6.2 CLAIM

Агент предлагает гипотезу, решение или готовность выполнить работу. CLAIM не считается фактом до проверки.

- `claim_type` — `hypothesis|solution|task_claim`;
- `statement` — string;
- `confidence` — number 0..1;
- `basis` — array of ссылок на knowledge_id/artifact_id, обосновывающих claim.

#### 6.3 RESULT

Фиксирует фактически полученный результат и ссылки на артефакты.

- `summary` — string;
- `artifacts` — array of artifact_id;
- `metrics` — object, опционально;
- `status` — `success|partial|failure`.

RESULT без хотя бы одного artifact_id или evidence-записи в envelope SHOULD считаться неполным и не может быть принят как verified без дополнительного запроса на подтверждение.

#### 6.4 QUESTION / ANSWER

- QUESTION: `question` — string; `context` — object, опционально; `blocking` — boolean (блокирует ли выполнение задачи отправителя).
- ANSWER: `answer` — string; `references` — array of knowledge_id/artifact_id, опционально. ANSWER MUST использовать `reply_to`, указывающий на message_id соответствующего QUESTION.

#### 6.5 PLAN

- `steps` — array of `{ step_id, description, depends_on: [step_id], assignee: agent_id|role|null }`;
- `estimated_effort` — string, опционально.

#### 6.6 REQUEST

Общий запрос действия/ресурса, не подпадающий под TASK (например, запрос доступа, запрос данных).

- `action` — string;
- `params` — object;
- `requires_approval` — boolean (см. RFC-1600 §8 Approval gates).

#### 6.7 VERIFY

Проверяющий агент оценивает RESULT и возвращает статус.

- `target_message_id` — message_id проверяемого RESULT (обязательно, эквивалент `reply_to`);
- `verdict` — `verified|rejected|inconclusive`;
- `rationale` — string;
- `evidence` — array, доказательства самой проверки.

#### 6.8 STATUS

Показывает состояние агента или задачи.

- `subject` — `agent|task`;
- `subject_id` — agent_id | task_id;
- `state` — `idle|working|blocked|waiting|completed|failed`;
- `detail` — string, опционально.

#### 6.9 ERROR

Использует структуру Error Protocol из RFC-1000 §8.

- `error_code` — string;
- `message` — string;
- `retryable` — boolean;
- `details` — object, опционально;
- `suggested_action` — string, опционально;
- `trace_id` — string.

#### 6.10 EVENT

Уведомление о факте, произошедшем в системе (не требует ответа).

- `event_type` — string (например `team_formed`, `role_changed`, `message_expired`);
- `data` — object.

#### 6.11 PROPOSAL

Общий механизм предложения решения, требующего согласия других участников (обобщает, например, ROLE_PROPOSAL из RFC-1200 §5).

- `proposal_type` — string;
- `details` — object;
- `voting_deadline` — ISO-8601, опционально;
- `decision_rule` — `unanimous|majority|weighted|coordinator_decides`, опционально.

#### 6.12 HANDOFF

Передача задачи другому агенту с причиной, текущим состоянием и незавершёнными пунктами.

- `task_id` — обязательно;
- `reason` — string;
- `current_state` — object;
- `remaining_items` — array of string;
- `to_agent` — agent_id.

#### 6.13 REVIEW

Оценка артефакта, плана или claim'а вне формального verification-потока (например, code review, peer review плана).

- `target` — artifact_id | message_id;
- `verdict` — `approve|request_changes|reject`;
- `comments` — array of string.

### 7. Correlation и threading

- `conversation_id` группирует все сообщения одного логического обмена (может охватывать несколько task_id, например уточняющие вопросы вокруг одной задачи).
- `task_id` связывает сообщение с конкретной сущностью Task (RFC-1800) и используется для маршрутизации по подписке на задачу.
- `reply_to` MUST указывать `message_id` сообщения, на которое дан прямой ответ (ANSWER → QUESTION, VERIFY → RESULT). Сообщение без предшественника (например, исходный TASK) имеет `reply_to: null`.
- Агент SHOULD сохранять `conversation_id` и `task_id` неизменными при цепочке ответов, если контекст не переходит в новую задачу.

### 8. Идемпотентность и дедупликация

- `message_id` служит ключом идемпотентности. Получатель MUST хранить окно недавно обработанных `message_id` (TTL окна — политика платформы, SHOULD быть не меньше ожидаемого окна ретраев транспорта) и игнорировать повторную доставку с тем же `message_id`.
- Побочные эффекты обработки сообщения (изменение состояния задачи, публикация в shared memory) MUST выполняться не более одного раза на уникальный `message_id`.
- Отправитель, ретраящий недоставленное сообщение, MUST переиспользовать тот же `message_id`, а не генерировать новый.

### 9. Приоритет

- `low` — best effort, может быть отложено при нагрузке;
- `normal` — приоритет по умолчанию;
- `high` — обрабатывается раньше очереди normal/low;
- `critical` — MAY прерывать текущий фокус агента (например, ERROR по критическому сбою или REQUEST на остановку опасного действия); получатель SHOULD подтвердить получение (STATUS/ACK) в первую очередь.

### 10. TTL и истечение сообщения

- Если `ttl` задан и `now > timestamp + ttl`, сообщение MUST считаться истёкшим и не доставляться / не обрабатываться получателем.
- Истёкшее сообщение, для которого отправитель запрашивал подтверждение доставки, SHOULD порождать `EVENT` с `event_type: "message_expired"`, адресованный отправителю.
- `ttl: null` означает отсутствие ограничения времени жизни.

### 11. Ограничение размера payload

- `payload` SHOULD не превышать заранее заданный платформой лимит (рекомендуемое значение по умолчанию — 32 KB).
- Данные, превышающие лимит (логи, дампы, большие вычисления), MUST сохраняться как Artifact (RFC-1300 §7) и передаваться в сообщении по ссылке (`artifact_id`), а не инлайн в payload.

### 12. Доставка при недоступности получателя

- Direct-сообщения к временно недоступному агенту MUST ставиться в очередь платформой и доставляться после его возврата в READY/WORKING, с экспоненциальным backoff между попытками.
- После исчерпания заданного числа попыток доставки платформа MUST переместить сообщение в dead-letter и уведомить отправителя ERROR-сообщением с `retryable: false`.
- Broadcast-сообщения не гарантируют доставку офлайн-подписчикам (см. §2).

### 13. Rate limiting и защита от спама

- Платформа MAY ограничивать частоту публикации сообщений на агента и на канал (число сообщений/сек или /мин).
- Превышение лимита MUST возвращать ERROR с `retryable: true` и `suggested_action`, указывающим на паузу перед повтором.

### 14. Правила

- Агент MUST указывать тип сообщения.
- Существенные результаты SHOULD содержать evidence.
- Ошибки MUST быть сообщены заинтересованным участникам.
- Ответы SHOULD ссылаться на исходное сообщение через reply_to.
- Сообщения MUST быть идемпотентными или иметь защиту от повторной обработки.
- Payload MUST соответствовать схеме своего `type` (§6).
- Данные, превышающие лимит размера, MUST выноситься в Artifact (§11).

### 15. Контроль шума

Агент SHOULD отвечать только если сообщение относится к его capability, назначенной задаче, команде или подписке на событие.

### 16. Версионирование протокола

- `protocol_version` следует семантике `MAJOR.MINOR`.
- MINOR-инкремент — обратно совместимое добавление (новый опциональный тип сообщения, новое опциональное поле payload). Получатель более старой MINOR-версии MUST игнорировать незнакомые поля.
- MAJOR-инкремент — breaking change (удаление/переименование обязательного поля, изменение семантики типа). Агент MUST согласовывать поддерживаемые MAJOR-версии через `compatibility` в manifest (RFC-1000 §2) перед использованием протокола.
- Платформа SHOULD поддерживать не менее одной предыдущей MAJOR-версии в течение публично объявленного переходного периода.

### 17. Безопасность

Подлинность поля `sender` и защита канала от подмены/чтения посторонними — предмет RFC-1600 (Trust boundaries, §2 «communication»). Настоящий RFC определяет только структуру и семантику сообщений, не аутентификацию.
