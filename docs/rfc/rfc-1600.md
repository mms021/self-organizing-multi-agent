# RFC-1600 — Security, Isolation and Trust Boundaries

**Status: Draft**

**Version: 0.3**

### 1. Базовый принцип

Самоорганизация не означает неограниченный доступ.

Принципы RFC-0000 (в частности P4 «минимальное начальное знание», P5 «самоопределение роли») описывают свободу агента исследовать платформу и предлагать себя на роли — но не подразумевают снятия ограничений на доступ к данным, инструментам или необратимым действиям. Discovery (RFC-1000) раскрывает, что существует и как этим пользоваться; настоящий RFC определяет, кому и при каких условиях разрешено это фактически использовать.

### 2. Trust boundaries

Разделяются:

- **agent identity** — граница между тем, кем агент заявляет себя (`sender` в envelope, RFC-1100 §5), и тем, кем он подтверждён платформой (`agent_id` + credential, выданные при регистрации, RFC-1400 §7). Сообщение, чей `sender` не подтверждён действительным credential, MUST отклоняться на транспортном уровне до попадания в протокол сообщений.
- **communication** — сам факт получения сообщения по каналу не означает доверия к его содержимому; получатель MUST применять минимальные права (§3) и контроль шума (RFC-1100 §15) прежде чем действовать по сообщению.
- **memory** — граница определяется project scope (RFC-1250 §8, §11): чтение/запись shared memory закрытого проекта MUST проверяться по членству, а не только по общей роли агента.
- **tools** — вызов инструмента ограничен его `permissions` (RFC-1000 §6); обнаружимость инструмента через Tool Registry не даёт автоматического права его вызывать.
- **external network** — см. §5.
- **credentials** — см. §7.
- **execution environment** — см. §4.

### 3. Минимальные права

Агент получает только необходимые permissions.

- Permission — тройка `(subject: agent_id, resource: tool_id|endpoint|project_id, action)`, выдаваемая платформой на основании capability profile при регистрации (RFC-1400 §7) и активных ролей агента (RFC-1200 §2).
- Permission MUST выдаваться под конкретный контекст (задача, команда или проект), а не бессрочно и глобально: завершение контекста — задачи, распад команды (RFC-1200 §13), revoke членства (RFC-1250 §14) — MUST аннулировать связанные с этим контекстом permissions.
- Запрос на расширение прав сверх выданных по умолчанию оформляется как `REQUEST` (RFC-1100 §6.6) с `requires_approval: true` и обрабатывается через Approval gates (§8).

Permission — модель данных:

- `permission_id`;
- `agent_id`;
- `resource` — `tool_id|endpoint|project_id`;
- `action`;
- `context_id` — task_id/team_id/project_id, породивший это право;
- `granted_at`;
- `expires_at` — ISO-8601 | null, синхронизирован с временем жизни `context_id`.

### 4. Sandbox

Непроверенные инструменты и код должны выполняться в изолированной среде.

- Инструмент MUST считаться непроверенным, пока не пройдёт квалификацию платформы (полное описание в Tool Registry, RFC-1000 §6, включая заявленный `risk`) либо не накопит историю успешных verified-результатов — аналогично тому, как формируется Selection Score (RFC-1500 §2).
- Выполнение непроверенного инструмента MUST происходить в изолированной среде без доступа к shared memory, credentials (§7) или external network (§5), кроме явно предоставленных на время конкретного вызова.
- Результат работы в sandbox — обычный `RESULT`/Artifact (RFC-1100 §6.3, RFC-1300 §7) и подлежит стандартной verification; сам факт исполнения в sandbox не повышает доверие к результату.

### 5. External access

Выход во внешние системы должен быть отдельной capability с явной политикой.

- Внешний доступ описывается отдельной записью в Tool Registry (RFC-1000 §6) с явным `risk` и списком разрешённых целей, а не общим правом «доступ в интернет».
- Каждый вызов внешнего доступа MUST журналироваться (§6) независимо от результата вызова.
- Необратимые внешние действия (платежи, отправка сообщений от имени платформы вовне, публикация во внешние системы) MUST проходить Approval gates (§8), а не выполняться по одному лишь наличию capability.

### 6. Audit

Системные и критические действия должны журналироваться.

Критические действия включают как минимум: регистрацию и retirement агента (RFC-1400 §7), назначение и отзыв роли (RFC-1200 §6, §13), создание, архивацию, смену видимости и смену владельца проекта (RFC-1250 §9, §14), verdict по `VERIFY` (RFC-1100 §6.7), решения Approval gates (§8), вызовы external access (§5).

AuditLogEntry — модель данных:

- `entry_id`;
- `actor` — agent_id, либо `platform`, если действие инициировано системой (например, автоматическая архивация проекта, RFC-1250 §9);
- `action` — тип действия;
- `context_id` — task_id/team_id/project_id, если применимо;
- `timestamp`;
- `details` — object; для действий, прошедших Approval gate (§8), MUST включать `approval_id`.

Audit log MUST быть неизменяемым (append-only, аналогично Reputation events, RFC-1500 §3) и доступен для чтения платформенному надзору независимо от `visibility` затронутого проекта (RFC-1250 §15). Рядовым агентам audit log недоступен, если иное не разрешено политикой платформы.

### 7. Secrets

Секреты не должны передаваться через обычные межагентные сообщения.

- Секрет, включая credential, выданный при регистрации (RFC-1400 §7), хранится в отдельном secret store — вне envelope сообщений (RFC-1100 §5) и вне shared memory (RFC-1300).
- Инструмент, которому требуется секрет, MUST ссылаться на него по `secret_id` в своей `input_schema` (RFC-1000 §6), а не получать значение секрета инлайн в payload.
- Секреты MUST поддерживать отзыв и ротацию; отзыв credential агента (например, при retirement, RFC-1400 §6) MUST немедленно делать его недействительным для аутентификации.
- Попадание секрета в обычное сообщение или shared memory (по ошибке агента) MUST трактоваться как `protocol_violation` (RFC-1500 §3) и требовать немедленной ротации затронутого секрета.

Credential — модель метаданных (само значение секрета в схему не входит и никогда не возвращается в API):

- `credential_id`;
- `agent_id`;
- `status` — `active|revoked|rotated`;
- `issued_at`;
- `rotated_from` — credential_id | null, ссылка на предшествующий credential при ротации.

### 8. Approval gates

Опасные или необратимые действия SHOULD требовать отдельного разрешения.

- К таким действиям относятся как минимум: необратимое удаление данных, финансовые операции, коммуникация вовне платформы от чужого имени (§5), изменение permissions (§3), смена владельца проекта (RFC-1250 §9).
- Запрос на подобное действие оформляется как `REQUEST` (RFC-1100 §6.6) с `requires_approval: true`; действие MUST оставаться в состоянии ожидания и не выполняться до явного одобрения.
- Approval выдаёт назначенный approver — платформенный оператор либо агент с ролью, явно наделённой этим правом (RFC-1200 §6, назначение извне), и не совпадающий с инициатором действия. Исключение — двусторонние действия, где approver'ом естественно выступает вторая сторона самого действия, а не независимый наблюдатель: например, передачу владения проектом (RFC-1250 §9) подтверждает именно принимающий новый owner.
- Если для контекста действия нет ни одного агента с ролью approver, отличного от инициатора, запрос MUST эскалироваться платформенному оператору, а не выполняться без approval.
- Решение MUST публиковаться как `EVENT` и подлежит Audit (§6).
- Отсутствие ответа approver'а в установленный срок MUST трактоваться как отказ (deny-by-default) — по аналогии с правилом RFC-1250 §6 для приглашений: молчание не равнозначно согласию.

Approval — модель данных:

- `approval_id`;
- `requested_by` — agent_id;
- `action_type`;
- `context_id` — task_id/team_id/project_id, если применимо;
- `status` — `pending|approved|denied|expired`;
- `approver_id` — agent_id | null (пока `pending`);
- `requested_at`;
- `decided_at` — ISO-8601 | null;
- `expires_at` — момент, после которого `pending` MUST переходить в `expired` (deny-by-default).

Повторный вызов `POST /approvals/{approval_id}/decide` с тем же idempotency key (RFC-1700 §3) не должен приводить к повторному применению решения.
