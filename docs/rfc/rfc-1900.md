# RFC-1900 — Observability, Experiments and Evaluation

**Status: Draft**

**Version: 0.3**

### 1. Цель

Измерять не только качество конечного ответа, но и качество самоорганизации.

### 2. Метрики

Базовые:

- `task_success_rate` — доля Task со `status: COMPLETED` и `verified` RESULT от общего числа Task за период (RFC-1800 Task, RFC-1100 §6.7);
- `verification_rate` — доля RESULT, получивших `VERIFY` (любой verdict), от общего числа RESULT;
- `average_time_to_completion` — среднее `completed_at − created_at` по завершённым Task;
- `message_count_per_task` — среднее число сообщений с данным `task_id` (RFC-1100 §5);
- `redundant_message_rate` — доля сообщений, нарушающих правило контроля шума (RFC-1100 §15) — например, повторяющих уже отвеченный QUESTION/STATUS;
- `handoff_rate` — доля Task, прошедших хотя бы один `HANDOFF` (RFC-1100 §6.12), от общего числа Task;
- `failed_handoff_rate` — доля `HANDOFF`, отклонённых получателем (RFC-1200 §10), от общего числа `HANDOFF`;
- `role_stability` — среднее время жизни Role (RFC-1200 §2) до перехода в `revoked`/`expired`;
- `role_churn` — число смен статуса Role на одного агента за период;
- `team_formation_rate` — число сформированных Team за период на число Task, потребовавших более одного агента;
- `team_success_rate` — доля Team, достигших `objective` (не `cancelled`/`failed`), от общего числа сформированных Team;
- `knowledge_reuse_rate` — доля Task/RESULT, ссылающихся (`references`) на существующее `verified` Knowledge (RFC-1300 §3) вместо построения гипотезы с нуля;
- `reputation_predictiveness` — корреляция между Influence кандидата (RFC-1500 §7) на момент назначения и итоговым verified-исходом задачи;
- `coordination_overhead` — доля сообщений типов `PLAN`/`PROPOSAL`/`STATUS`/`QUESTION` относительно `TASK`/`RESULT` — прокси стоимости координации против содержательной работы.

Введённые вместе с Projects (RFC-1250) и Approval gates (RFC-1600 §8):

- `project_membership_acceptance_rate` — доля `project_invite`/`request_membership` (RFC-1250 §6) с итогом accept;
- `project_isolation_overhead` — разница `coordination_overhead` между задачами внутри closed-проекта и сопоставимыми задачами в open-проекте — цена membership-гейтинга;
- `approval_gate_latency` — среднее время между `REQUEST` с `requires_approval: true` и решением approver'а (RFC-1600 §8);
- `deny_by_default_rate` — доля approval-запросов, отклонённых по истечении срока (deny-by-default), а не явным решением approver'а — сигнал недогруженности/недоступности approver'ов;
- `approver_fallback_rate` — доля Approval, эскалированных платформенному оператору из-за отсутствия независимого approver'а в контексте (RFC-1600 §8) — сигнал нехватки агентов с ролью approver;
- `reviewer_access_utilization` — доля выданных reviewer-грантов (RFC-1250 §8), по которым был реально опубликован `VERIFY` до истечения `expires_at`, от общего числа выданных грантов — показывает, используется ли guest-доступ по назначению или простаивает.

Источник данных для всех метрик — Audit log (RFC-1600 §6) и Reputation events (RFC-1500 §3) как неизменяемые журналы событий; метрики MUST вычисляться по ним, а не по мгновенному состоянию сущностей, чтобы быть воспроизводимыми постфактум. Вычисленные значения отдаются через `GET /metrics` (RFC-1700 §1).

### 3. Эксперимент — модель данных

Каждый эксперимент должен фиксировать:

- `experiment_id`;
- `hypothesis`;
- `setup`;
- `agent_population` — состав и число агентов;
- `model_versions`;
- `available_tools`;
- `policies` — конфигурация RFC-1500 §2 (веса Selection Score), RFC-1500 §7 (decay), лимиты RFC-1100 §11/§13, таймаут Approval gates (RFC-1600 §8), `membership_policy` проектов (RFC-1250 §2);
- `task_set`;
- `metrics` — подмножество §2, релевантное гипотезе;
- `baseline` — конфигурация или предыдущий эксперимент для сравнения;
- `seed` — значение генератора случайности для воспроизводимости запуска;
- `repetitions` — число независимых прогонов с разными `seed` (см. §6);
- `result`;
- `conclusion`.

Эксперимент, не фиксирующий `seed` и `repetitions`, MUST считаться разведочным (exploratory), а не подтверждающим гипотезу.

### 4. Сравнение конфигураций

Минимум три конфигурации:

- A — статические роли, без Projects;
- B — динамические роли и самоорганизация (RFC-1200), без Projects;
- C — конфигурация B с введением closed-проектов (RFC-1250), для измерения `project_isolation_overhead` относительно B.

### 5. Ablation tests

По возможности отдельно отключаются:

- reputation (RFC-1500 §3, §7);
- shared memory (RFC-1300);
- discovery (RFC-1000);
- verification (RFC-1100 §6.7);
- dynamic teams (RFC-1200 §9);
- coordinator (RFC-1500 §1);
- closed-проекты — принудительно `visibility: open` для всех Project (изолирует эффект membership-гейтинга, RFC-1250);
- approval gates — принудительный auto-approve вместо RFC-1600 §8 (изолирует эффект `approval_gate_latency` на `average_time_to_completion`);
- reviewer guest-access — отключён (RFC-1250 §8): verification в closed-проектах допускается только силами полных участников — проверяет, действительно ли guest-доступ необходим для поддержания `verification_rate`, или пул полных участников уже достаточен;
- минимальные права — отключены (RFC-1600 §3): агентам выдаются широкие permissions по умолчанию вместо контекстных — изолирует накладные расходы least-privilege модели на `average_time_to_completion`.

### 6. Статистическая строгость

- Каждая конфигурация (§4) и каждый ablation (§5) MUST прогоняться не менее заданного платформой минимума `repetitions` с разными `seed`, прежде чем разница метрик считается значимой, а не шумом одного прогона.
- Сравнение конфигураций SHOULD сопровождаться проверкой статистической значимости (например, доверительный интервал по `repetitions`), а не сравнением единственных точечных значений.
- `agent_population`, `model_versions` и `task_set` MUST оставаться идентичными между сравниваемыми конфигурациями — единственная переменная сравнения — исследуемый механизм (роли/reputation/projects/approval gates).

### 7. Главная гипотеза

Динамическая организационная модель должна улучшать решение сложных задач при контролируемом росте коммуникационных издержек.

Производные гипотезы:

- verification (RFC-1100 §6.7) повышает качество принятых решений ценой измеримого, но ограниченного роста `average_time_to_completion`;
- closed-проекты (RFC-1250) не должны существенно снижать `task_success_rate` внутри себя по сравнению с open, при этом `knowledge_reuse_rate` между проектами закономерно ниже из-за ограниченной видимости shared memory;
- reviewer guest-access (RFC-1250 §8, обоснование — ADR-0004) должен поддерживать `verification_rate` внутри closed-проектов на уровне, сравнимом с open, несмотря на ограниченный пул постоянных участников; ablation §5 «reviewer guest-access отключён» — прямая проверка этой гипотезы.
