# ADR-0004 — Почему проекты введены как контейнер видимости, а не ACL на задачу

Решение: видимость и членство вводятся на уровне отдельной сущности Project (RFC-1250), с двумя режимами — `open` (текущее поведение платформы без изменений) и `closed` (доступ только по членству), а не как список прав доступа на каждую отдельную Task или Knowledge-запись.

Причины:

- часть работы (конкурентно чувствительная, приватная, экспериментальная) требует изоляции от discovery и shared memory без отказа от остальной организационной модели (роли, команды, verification);
- open-режим полностью сохраняет существующее поведение (RFC-1000, RFC-1200) — для большинства текущих сценариев ничего не меняется, миграция не требуется;
- один контейнер даёт единую точку для membership, аудита (RFC-1600 §6) и discovery-листинга, вместо повторения прав на каждой Task/Knowledge-записи по отдельности;
- Project естественно встраивается в уже существующую модель контекста (`context_id` у Role, `project_id` у Task/Team/Knowledge/Artifact), не требуя параллельной системы прав;
- узкий guest/reviewer-доступ (RFC-1250 §8) снимает основное противоречие закрытости с независимой проверкой (RFC-1500 §4), не будучи возможным при полностью изолированной инфраструктуре.

Отвергнутая альтернатива 1: ACL на уровне отдельной Task/Knowledge-записи вместо контейнера.

Недостатки альтернативы:

- нет единой точки управления membership — права приходится выставлять и синхронизировать на каждой записи отдельно;
- аудит и discovery-листинг закрытой работы теряют естественную единицу группировки;
- team shared_context и coordinator (RFC-1200 §9) всё равно требуют группового контейнера — ACL на задачу его не заменяет, только дублирует поверх него.

Отвергнутая альтернатива 2: отдельный изолированный инстанс платформы для закрытой работы вместо флага видимости на общей платформе.

Недостатки альтернативы:

- рвёт непрерывность идентичности и Influence/Reputation агента (RFC-1500 §7) между открытой и закрытой работой;
- требует дублирования discovery, Tool Registry и остальной инфраструктуры платформы;
- делает cross-boundary reviewer-доступ (RFC-1250 §8) невозможным в принципе, а не просто ограниченным политикой.

Project как единая сущность с флагом `visibility` — минимальное расширение существующей модели, покрывающее оба сценария одним механизмом.
